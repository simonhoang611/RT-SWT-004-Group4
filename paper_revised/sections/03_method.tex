\section{Methodology}
\label{sec:method}

Fig.~\ref{fig:flow} in Appendix~\ref{app:more} shows how the files pass through generation and analysis, with the denominator of each analysis.

\subsection{Dataset Construction}

The dataset pairs 261 project-maintained reference files (.feature files) from three open-source projects with 261 user stories. The stories were not collected from a backlog. They were reverse-engineered from the feature files: GPT-5.4-mini (temperature 0) received the text of each feature file and was asked to write one Connextra-style story (``As a [role], I want [feature], so that [benefit]'') with as many acceptance criteria as needed to cover all of its scenarios. Only the first 15,000 characters of each file were passed to the model. This truncated 84 of the 261 files, all of them from Apache Fineract (84 of its 100 files, whose stored references have a median length of about 30,000 characters). Each generated file is scored against the whole stored reference, not against that prefix; for 23 Fineract files the stored reference is itself shorter than the upstream file. Sections~\ref{sec:threats} and~\ref{sec:res-b1} discuss and measure the leakage risk this creates.

\textbf{Sources and selection.} The files were collected in two batches: a random sample of 100 files downloaded on 28 June 2026 and 161 further files drawn at random from the clones of Table~\ref{tab:dataset}. In the first batch some stored references differ from their upstream files; scoring against the full upstream files leaves every RQ1 decision unchanged.

The projects were chosen for domain and style diversity (Section~\ref{sec:intro}). The benchmark is a deliberately heterogeneous sample of mature public English-language repositories, not a representative sample of BDD practice.

\subsection{Model and Prompt Configuration}

All generation requests specified gpt-5.4-mini-2026-03-17~\cite{openai_gpt54mini} through the OpenAI Chat Completions API~\cite{openai_chat_api} with temperature 0; the returned model name was recorded for C1, C2 and the rerun below but not for the original C0. The requests set no maximum-token cap, which deviates from the research proposal's planned cap of 1,500 output tokens. The original condition (C0) is same-project one-shot prompting: each project has its own system message and one example pair (user story and reference Gherkin) from the same project (Listing~\ref{lst:prompt} in Appendix~\ref{app:details}). The three example files (ids 2, 102 and 202) are also members of the dataset, and their own generated files score 1.000, 0.997 and 1.000 on the metric below. The primary analysis therefore excludes them ($N = 258$); results for all 261 files are reported alongside, and no generated file was excluded because of its content.

\textbf{Prompt ablation.} C1 is zero-shot: the same system message and wording, with the example block and the sentence referring to it removed. C2 is one-shot with a different exemplar per project (ids 86, 119 and 203), drawn with a fixed random seed (2026) from the remaining files of each project before any C2 output existed. Model, temperature, system messages and output clean-up are identical in all conditions, and the ablation is analysed on the 255 files that are not an exemplar in any condition. Its analysis plan, written before the C1 and C2 runs of 16 October 2026 and released with its SHA-256 hash, specifies paired Wilcoxon signed-rank tests on per-file cosine and exact McNemar tests on parser outcomes, each against C0 and Holm-corrected. All three conditions were scored with an ONNX export of the encoder that reproduces the original C0 scores.

\textbf{Same-time rerun.} Because the original C0 ran on 19 July 2026, three months before C1 and C2, we ran C0, C1 and C2 again on 28 October 2026 with one script and one logging path, on all 261 stories and four more times on a subset of 60 stories (20 per project, drawn with a fixed seed from the files that are not an exemplar in C0 or C2). The same run included C0cap, C0 with the proposal's cap of 1,500 output tokens, on all 261 stories (Section~\ref{sec:threats}). The 1,764 requests were shuffled with a fixed seed and sent by four parallel workers, so the conditions are interleaved in time. The analysis plan, committed with its SHA-256 hash before the first request, repeats the ablation tests against the new C0 and measures run-to-run variation on the 60 files. It fixes that the original C0 stays the primary result and that a paired median difference smaller than the pooled within-file SD is not reported as a prompt effect.

\subsection{Generation and Recording Pipeline}

The pipeline builds the prompt for the story's project, calls the API and removes a Markdown code fence only when the model wraps its output in one; no generated text is edited by hand, and each call is logged with its timestamp and token counts. The C0 notebook used a timeout of 600 s and retried any failed request, including rate-limit errors, after a 60 s wait with no limit on the number of attempts; the C1, C2 and rerun scripts made up to five attempts per story with waits between 5 and 60 s. These scripts treated an empty output as a failure, and a story still failing after a resumed run would have stayed in the denominator as a parser FAIL. None of these events occurred: all C1, C2 and rerun requests succeeded at the first attempt, all 261 C0 requests returned an output, and no output in any condition was empty.

\subsection{Metric 1: Skeleton Cosine Similarity}
\label{sec:metric1}

Skeleton cosine similarity compares a generated file with its reference after reducing both to a skeleton. The skeleton keeps every line that begins with a Gherkin keyword (Feature, Background, Scenario, Given, When, Then, And, But), including the keyword itself. It removes tags, replaces every double-quoted string with \texttt{<PARAM>} and every number with \texttt{<NUM>}, and drops all other lines, so data tables, doc strings and Examples tables disappear (Table~\ref{tab:skeleton} in Appendix~\ref{app:details}). Each skeleton is encoded as a whole with all-MiniLM-L6-v2~\cite{reimers2019,minilm_card}, which mean-pools token embeddings and truncates its input at 256 word-piece tokens. With $g$ and $r$ the embeddings of the generated and reference skeletons,
\begin{equation}
\mathrm{SkelCos}(g, r) = \frac{g \cdot r}{\lVert g \rVert \lVert r \rVert}.
\end{equation}

Two properties of this design limit what the metric can show. First, masking makes the score blind to changed numbers and quoted values by construction. Second, truncation means that the score often reflects only the start of a file: 174 of the 258 reference skeletons (67.4\%) and 166 of the 258 generated skeletons (64.3\%) exceed 256 tokens, including 94 of the 99 Fineract references (median 3,506 tokens). The metric therefore measures the structural resemblance of keyword lines to the reference, not the preservation of business intent; evidence on business intent comes only from the defect audit (Section~\ref{sec:method-audit}), against which Section~\ref{sec:res-defects} checks the metric.

The reference point of 0.85 was fixed in the research proposal before the full run. It was not calibrated against human judgement, and it is not an acceptance criterion: no labels independent of the scores were available to calibrate a cut-off. No prior study reports skeleton cosine with this encoder for Gherkin, and the proposal's pilot (30 stories, ids 1--10, 101--110 and 201--210, mean 0.859) used stories that are also part of the evaluated set. We therefore treat 0.85 as an operational reference point and report how the conclusions change between 0.80 and 0.90 (Section~\ref{sec:res-b3}).

\subsection{Metric 2: Parser Compliance}

Parser compliance is the share of generated files that the behave Gherkin parser accepts. For a generated set $S$,
\begin{equation}
\mathrm{ESR} = \frac{|\{s \in S \mid \text{parse}(s) = \text{PASS}\}|}{|S|}.
\end{equation}
We keep the proposal's name, executable syntax rate (ESR), but the check is narrower: each file is passed to behave's parser (behave 1.3.3~\cite{behave133}) without step definitions, so no step is matched or executed, and a PASS means only that the file is valid Gherkin, not that its scenarios are complete, executable against the application or correct. A dry run (\mbox{behave -{}-dry-run}) is not used, because without a steps directory it stops with a configuration error before parsing the file. Versions 1.2.6 and 1.3.3 of behave agree on every generated file.

\subsection{Defect Audit and Structural Checks}
\label{sec:method-audit}

Because neither metric checks business intent, we audited high-scoring outputs for defects. Of the 258 analysed files, 136 have a skeleton cosine of at least 0.85. From these we drew 20 files per project with a fixed seed (2026), giving 60 files. Each file was labelled against its user story and acceptance criteria; the reference was consulted only for project conventions. For each criterion the labeller recorded a business-logic facet (numbers, conditions, outcomes) and a temporal/causal facet (preconditions, triggers, order of states). Each defect received a severity from 0 (none) to 3 (the test would pass on a system that violates the criterion), and a file counts as defective if it has at least one defect of severity 2 or higher. Line-level evidence was recorded for each defect.

The labels were drafted by an AI coding assistant (OpenAI Codex) and then reviewed by a second author, who retained all of them unchanged; that review was recorded as one confirmation covering all 60 files, not as a decision with reasons per file. To estimate reliability, the first author, who reports not having seen the labels or their aggregate rates before rating, labelled a subset of 15 files fixed in advance (6 Sylius, 3 Fineract, 6 Diaspora) with the same guide, and we report Cohen's $\kappa$~\cite{cohen1960} between these labels and the reviewed labels. This is agreement between one independent human rater and AI-drafted, human-reviewed labels, not between two independent human raters. Because both values fell below the 0.7 required by our protocol, the reviewing author and the independent rater then held the protocol's consensus round on the 15 files and recorded a final label, severity, reason and line evidence for each of the 30 file--facet decisions.

Separately, an automated check flags four keyword-order violations per scenario, and a perturbation test applied eight defect-seeding operators to 120 scenarios extracted from the reference files and compared each mutant with its original using the same metric (Appendix~\ref{app:perturb}).

\subsection{Statistical Analysis Plan}

The confirmatory tests use $\alpha = 0.05$ and follow standard guidance on matching tests to data properties~\cite{arcuri2011}. Effect sizes are reported without categorical labels such as small or large and are interpreted through their magnitude and 95\% confidence intervals: an exact interval for $\delta$, derived from the Clopper--Pearson interval of the share of files above 0.85, and percentile bootstrap intervals (10,000 resamples, seed 2026) for $\eta^2_H$, Spearman's $\rho$, Cohen's $\kappa$ (resampling files) and, outside the rerun plan, the median paired differences of the ablation.

\textbf{RQ1: exact sign test, with the Wilcoxon test as sensitivity analysis.} $H_0$: the median skeleton cosine is at most 0.85; $H_1$: it exceeds 0.85. The proposal phrased these hypotheses in terms of the mean and pre-registered a one-sided one-sample Wilcoxon signed-rank test on $x_i - 0.85$, which addresses the median only if the differences are symmetric; they are not (Section~\ref{sec:results}). The median is therefore tested with the exact one-sided sign test~\cite{agresti2002} and estimated with a 95\% percentile bootstrap interval~\cite{efron1993}, and the Wilcoxon test is reported as a sensitivity analysis. As effect size we report $\delta = P(x > 0.85) - P(x < 0.85)$. A non-significant result is read as insufficient evidence for performance above the reference point, not as evidence of poor performance.

\textbf{RQ2: exact binomial test.} Each file has a binary parser outcome. We test $H_0$: $p_{\mathrm{ESR}} \le 0.80$ against $H_1$: $p_{\mathrm{ESR}} > 0.80$~\cite{agresti2002} and report a 95\% Clopper--Pearson interval~\cite{clopper1934} and the risk difference from 0.80.

\textbf{Exploratory analyses.} The following analyses were planned after the reviews and are exploratory. Per-project differences are tested with a Kruskal--Wallis test~\cite{kruskal1952}, reported with $\eta^2_H = (H - k + 1)/(n - k)$ and followed by pairwise two-sided Mann--Whitney tests with Holm correction~\cite{holm1979}. Reference-point sensitivity repeats the RQ1 test for reference points from 0.80 to 0.90. Lexical leakage is measured as the share of distinct word trigrams of the reference that also occur in the story, related to skeleton cosine with Spearman's $\rho$.
